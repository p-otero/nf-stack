# Forms

Part of the `eskais-ui` skill.

## Forms

`npx shadcn add @eskais/form` brings react-hook-form and `@hookform/resolvers`. The schema is any Standard Schema: Zod, Valibot, ArkType or Effect Schema.

- **Fields.** `<FormField name label description required>` wraps one control and binds it by `name`: `Input`, `Textarea`, `NumberInput`, `Select`, `Combobox`, `Checkbox`, `Switch`, `RadioGroup`, `Slider`, `DatePicker`, `SegmentedControl`, `ToggleGroup`, `TokenInput` (a `string[]` with `tokenType`). Checkbox and Switch bind `checked`, the rest `value`/`onValueChange`. A control's own module can add an adapter to `formControlAdapters` (exported from `field` and `form`). For your own control pass `bind="checked"`, an adapter, or `render={(field) => …}`; inside it, `useFormField()` returns `value`, `onChange`, `invalid`, `error`. Give every field a default value.
- **Required.** A field the schema rejects when empty gets an `aria-hidden` asterisk (`text-destructive`) and its control `required`. Detection probes the schema synchronously with the default values, so it needs a schema that reports every issue (Zod, Valibot, ArkType); otherwise pass `required`. `required={false}` drops the marker. `requiredLabel="required"` (on `Form` or `FormField`, in the page's language) adds words for screen readers; they join the field's name, so agents and `getByRole` see "Email required". Unset, screen readers announce the control's own required state.
- **Typed names.** `const { Form, FormField, useFormInstance, useFormWatch, useFormFieldArray } = createForm<typeof schema>()` at module level: the same components, with `name` checked against the schema's input (`tags.${number}.label` included).

  ```tsx
  const schema = z.object({ name: z.string().min(1), email: z.email() })
  const Profile = createForm<typeof schema>()

  <Profile.Form schema={schema} defaultValues={{ name: "", email: "" }} onSubmit={save} label="Profile">
    <Profile.FormField name="email" label="Email"><Input type="email" /></Profile.FormField>
  </Profile.Form>
  ```

- **Submit.** `onSubmit(values, { setError })` gets the parsed values. A returned Promise shows the submit Button's `loading`, disables the fields (`disableWhilePending={false}` keeps them) and ignores a second submit. Don't add your own pending state.
- **Server errors.** Throw `new FormServerError(message, { email: "Taken" })`, an object `{ fieldErrors, message }`, or a Standard Schema issue list (`toFormErrors` reads all three). Field errors land on their fields; the message, and errors for fields that aren't rendered, in `<FormRootError />` (an `Alert tone="destructive" live`). Any other error shows its `message` there. Focus then moves to the first invalid field, or to the root error.
- **Messages.** English by default. `messages={formMessagesEs}`, your own dictionary (strings with `{min}`, `{max}`, `{label}`, or functions), or a function of the issue for any i18n library: `messages={(issue) => t(`form.${issue.code}`, { ...issue.params, field: issue.label })}`, or `createFormMessages(t)`. Return `undefined` to fall back to the defaults, then to the schema's own message. `<FormField messages>` wins over the form's.
- **Issues.** `{ code, field, label?, params, message? }`. Codes: `required` (an empty value), `minLength`/`maxLength` and `minItems`/`maxItems` (`params.min`/`max`), `min`/`max`, `email`, `url`, `pattern`, `invalid` (no known validator; `message` is the schema's), `server` (a plain-text server error). A schema message that looks like a key (`"form.email.taken"`) is its own code, so schemas can carry translation keys. A server error may be `{ code, params?, message? }` instead of text: `{ fieldErrors: { email: { code: "email.taken" } } }`.
- **Schemas without codes.** Effect Schema (and any Standard Schema whose issues carry only `message` and `path`) reaches `messages` as `invalid`, or `required` for an empty value. Put the code in the message: `formIssueMessage(code, params)` writes `@@form:code` or `@@form:code|{json}` (a reserved prefix, so it never reads prose as a code), and the form reads it back as `issue.code` and `issue.params`, with `issue.message` `undefined`. Every code round-trips, built-in or dotted. The earlier `code|{json}` and bare dotted keys still read. Use a dotted key for your i18n library or a built-in code for the built-in dictionaries: `Schema.String.pipe(Schema.minLength(3, { message: () => formIssueMessage("minLength", { min: 3 }) }))`. Without a translation, the key shows without its params. There is no Effect adapter: its issues hold nothing more to read.
- **Actions.** `<FormActions submitLabel pendingLabel cancel onCancel secondaryAction>` stacks on narrow screens. For a busy state outside the form, `disabled` disables submit and cancel, `submitDisabled` only submit, and `pending` forces the pending look; with any of them the form doesn't submit, from Enter, code or an agent. `tone="destructive"` requires `confirm`, the sentence an agent must show a person; it becomes `data-agent-confirm` on the submit button.
- **In a dialog.** `FormDialog` takes the Form props plus `trigger` (or `open`/`onOpenChange`), `title`, `description`, `size`, `submitLabel`, `cancelLabel`, `pendingLabel`, `secondaryAction` and `returnFocus`. `onOpenChange(open, details)` and `onOpenChangeComplete(open, details)` (after the transition) say why in `details.reason`: `submit`, `cancel`, `escape`, `outside`, `dismiss`, or `trigger` when it opens. The body scrolls between the header and the actions; on narrow screens it is a bottom sheet. It closes when `onSubmit` resolves, and a thrown error keeps it open. Escape, outside presses and Cancel do nothing while pending. `confirmDiscard="Discard changes?"` (with `discardLabel`, `keepEditingLabel`) asks before closing with unsaved changes. `reviewStep={{ render: (values) => …, editLabel, confirmLabel }}` validates, shows a review, and runs `onSubmit` on confirm; a server field error returns to the fields. `prepare: async (values, { form }) => ({ values } | { error })` runs first with the submit pending. Returned `values` are reviewed and submitted and also written into the form (`setValue` per top-level key), so Edit shows them; they must pass the schema as input too. Or write through `form.setValue` and return nothing: the form's values are parsed again and reviewed. Returned `values` win over what `prepare` wrote. `editable: (state) => !state.error` hides Edit, and `title: (step) => step === "review" ? "Check the order" : "New order"` follows the step.
- **Instance.** Inside a `Form`, `useFormInstance<Values>()` is the typed react-hook-form instance (`trigger`, `setValue`, `getValues`, `control`, `formState`). Its `watch` re-renders the Form, not your component: use `useFormWatch(name)`. `useFormFieldArray(name, options)` wraps `useFieldArray`; key rows by `field.id` (or, when the items carry their own `id`, by the property `keyName: "fieldKey"` names) and name fields `` `tags.${index}.label` ``. `form-context.ts` is internal: import only from `@/components/ui/form`.
- **Steps.** `StepDialog` (or `StepForm` inline) splits one schema into `steps: { id, title, description?, render: (form) => …, fields?, validate? }[]`. Next and Enter validate only that step's fields (`fields`, or its mounted `FormField`s) and then `validate(values)`, which returns nothing or an error in any shape `onSubmit` throws. Back keeps values. The last step submits through `onSubmit`; a failed validation or a server field error returns to the step that holds the field. Focus moves to the step heading on Next and Back. The progress list marks the current step with `aria-current="step"`. `onStepChange(id, { index, previous, direction })`, `step`/`defaultStep`, and `labels` (`next`, `back`, `submit`, `progress`, `cancel`) in the page's language. Agents press Next, Back and the submit button by name. `StepDialog` `onOpenChange(open, details)` gives `details.reason` (`submit`, `done`, `cancel`, `escape`, `outside`, `dismiss`, `trigger`). To show the outcome in the dialog instead of closing it, pass `resultStep={{ title, render: (result, { close, restart }) => … }}`: `result` is what `onSubmit` resolved with, focus moves to the result heading, Done (`labels.done`) and Escape close it (reason `done` or `escape`), and `restart()` starts over from step 1 with the default values.
- **Label placement.** `labelPlacement` on `Form` sets a default for its fields, plain `Field`s in the floating layout included; `labelPlacement` on a `FormField` or `Field` overrides it (`top` keeps the label above); see "Floating labels".
- **Agents.** Fields are their own UI SDK parts, so agents fill them by label. With a `label` (or `aria-labelledby`), the form itself offers `submit` and `reset`; a destructive form hides them so the gated button is the only way.

## Floating labels

`<Field labelPlacement="top" | "in" | "on">` (and `Form`/`FormField labelPlacement`) moves the `FieldLabel`. It stays a real `<label>`, so people, screen readers and agents name the control the same way in every placement.

- **`top`** (default): above the control.
- **`in`**: inside the control like a placeholder; it floats up and shrinks on focus, once the control has a value, or while its popup is open. The control grows by `--field-label-offset` to fit both, so nothing moves when it floats. A placeholder would sit under the resting label, so it shows only while the control is focused: write it as a format hint, never as the only instructions.
- **`on`**: on the control's top border, cutting the line. It is drawn over `--field-label-surface`, which cards (`field-label-surface-card`), dialogs and drawers (`field-label-surface-popover`) and floating surfaces set to their fill; the page background otherwise. Set it yourself on another coloured surface. Placeholders show as usual.
- **Controls.** Input, InputGroup (the label starts after a leading icon), Textarea, Select, NativeSelect, NumberInput, DatePicker, DateTimePicker, Combobox and TokenInput (it grows with its chips; `on` leaves room under the label). A Form's default reaches only those, in a `FormField` or in a plain `Field` inside the Form (a read-only Textarea, say) that doesn't set its own and is in the floating layout: a `FieldLabel`, then the control, then only a `FieldDescription` or `FieldError`, with no padding in its `className` (the label is placed from the Field's box, so padding or other content would put it over the value). Any other Field, and a padded `FormField`, keeps its label on top unless it sets `labelPlacement` itself; Checkbox, Switch, RadioGroup, Slider, SegmentedControl and ToggleGroup keep their label on top. A control of your own floats on `:placeholder-shown`, `data-filled` or `data-open`: give its input `useFloatingPlaceholder(placeholder)` and add it to `floatingLabelControls` so a Form's default applies.
- **State.** The description and error stay below. An invalid field turns the label `destructive`; a focused one `foreground`. The motion is a transform, collapsed under reduced motion. The states come from the theme's `field-floated` variant, so update `@eskais/theme` with the components.
